# src/plugins/

## Responsibility
This directory contains all bot plugins, each implementing a distinct feature set (admin, automod, integrations, interlink, moderation, tickets, utility). Plugins are self-contained modules that extend bot functionality via the PluginManager, encapsulating commands, events, and plugin‑specific logic. Plugins can be built-in (located in src/plugins/<name>) or installed (located in data/plugins/<name>) and may run in the main process or in sandboxed worker processes for isolation.

## Design
- **Plugin contract**: Each plugin exports a class extending `src/core/Plugin.js` with static `id`, `version`, `dependencies` array, optional `requiredIntents`/`requiredPartials`, and lifecycle methods `onLoad`, `onUnload`, `onEnable`, `onDisable`.
- **Plugin manager**: `src/core/PluginManager.js` discovers plugins via `scanPlugins`, loads them by dynamically importing `plugin.js`, instantiates the class, and registers it in internal maps (`_pluginRegistry`, `plugins`). It handles dependency resolution, enabling/disabling, and capability indexing for sandboxed plugins.
- **Lifecycle management**: Manager resolves dependencies with topological sort (`_sortByDependencies`), then enables plugins in parallelized topological levels. Plugins auto‑load commands from `./commands/` and events from `./events/` via the base `Plugin` class.
- **Sandboxed plugins**: Installed plugins may run in worker processes via `src/core/worker/workerHost.js` and `workerChild.js`. Capabilities are declared in `pluginManifest.json` and enforced by the worker host.
- **Extension points**: Plugins can register socket handlers through `manager.registerSocketHandler` for admin‑style RPC calls over Unix socket.
- **Manifest integrity**: Plugin integrity is verified via SHA-256 hashes in `plugin-manifest.json` (regenerated by `pnpm manifest`).

## Flow
1. **Discovery**: `PluginManager.scanPlugins` reads `./src/plugins/*/plugin.js` and optionally `./data/plugins/*/plugin.js` to identify available plugins.
2. **Loading**: For each plugin ID, `loadPlugin` dynamically imports `plugin.js`, stores the class in `_pluginRegistry`, creates an instance with `(client, manager)`, sets its directory, and calls `onLoad`.
3. **Dependency resolution**: Before enabling, manager topologically sorts plugin IDs using declared `dependencies` and invokes `visit` to order loading.
4. **Enabling**: For each plugin in sorted order (grouped by dependency level for parallelization), `enablePlugin` calls `onEnable`, which loads commands/events (via base class `_loadCommands`/`_loadEvents`) and registers any socket handlers. For sandboxed plugins, a worker process is spawned.
5. **Runtime**: Enabled plugins interact with the Discord `client`, event `bus`, and `manager`; commands are added to `client.commands`; listeners are attached to the client. Sandboxed plugins communicate via IPC with the worker host.
6. **Disabling/Cleanup**: `disablePlugin` calls `onDisable` to remove commands, listeners, and clean up schedulers; `unloadPlugin` additionally calls `onUnload` and removes the instance from `plugins`. For sandboxed plugins, the worker process is terminated.
7. **Command synchronization**: After plugin changes, `PluginManager._syncDiscordCommands` updates application commands with Discord (guild‑specific for instant updates, otherwise global).

## Integration
- **src/core**: Plugins import the base `Plugin` class; they may also use `pluginDownloader.js` (for install/uninstall), `manifest.js`, `workerHost.js`, and `PluginManager` (via `this.manager`).
- **src/utils**: Common utilities (logger, config helpers, db wrappers) are imported as needed for plugin logic.
- **src/db**: Plugins that persist data import Prisma models or database clients from `src/db` to perform CRUD operations.
- **Discord.js**: The `client` instance (passed to the plugin constructor) provides access to Discord API interactions (commands, events, REST).
- **Worker system**: Sandboxed plugins (e.g., interlink) run in isolated processes via `src/core/worker/workerHost.js`, communicating over IPC with capability‑based access control.
- **Configuration**: Plugin behavior is configured via `config.plugins` (enabled list, optional directory, registry file) loaded from environment and config files.
