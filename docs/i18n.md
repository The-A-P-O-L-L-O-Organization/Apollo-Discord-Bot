# Apollo i18n Translator Guide

This guide covers how to add or fix bot translations. The bot uses
[i18next](https://www.i18next.com/) with per-plugin namespaces and three pilot
locales: `en-US`, `es-ES`, and `de`.

## Concepts

- **Namespace = plugin id.** Each plugin owns one namespace named after its
  plugin id (`utility`, `moderation`, `tickets`, `automod`, `admin`,
  `integrations`, `interlink`). Core shared strings live in the `common`
  namespace under `src/i18n/dictionaries/`.
- **en-US is canonical.** Every key must exist in the `en-US` file first.
  `pnpm lint:locales` fails CI when any other locale is missing a key that
  exists in `en-US`.
- **Fallback chain.** Resolution order for a guild is stored guild locale,
  then interaction `locale`, then `guildLocale`, then `en-US`. A missing key
  in any locale falls back to the `en-US` value, and a wholly missing key
  renders the key itself (the bot never throws on a missing string).
- **File layout.** First-party plugins keep locales at
  `src/plugins/<id>/locales/<BCP47>/common.json`. Third-party plugins keep
  them at `data/plugins/<id>/locales/<BCP47>/common.json` and reach them
  through the host `api:i18n` RPC capability, never worker filesystem access.

## Adding a new string

1. Add the key to the `en-US` file with the English text.
2. Use `{{variable}}` placeholders for interpolated values, never single
   braces. `{name}` renders literally; `{{name}}` is replaced by i18next.
   (One legacy exception: core `welcome.message` still uses `{user}` and
   `{server}` because it mirrors the `config.welcome.message` template that
   is formatted with manual string replacement.)
3. Copy the key to the `es-ES` and `de` files and translate the text,
   keeping the exact same `{{variable}}` set.
4. Run `pnpm lint:locales` before opening the PR.

## Plurals

Plural forms use i18next suffixes: `_one`, `_few`, `_many`, `_other`.
Always define at least `_one` and `_other` in `en-US`, and mirror every
suffixed key the source requests in the other locales. Call sites pass
`{ count }`; i18next selects the suffix per locale plural rules.

## Concurrency

`t()` calls are synchronous reads against already-loaded bundles, so
concurrent command executions never race. Always resolve the locale first
with `resolveLocale()` (or `getGuildLocale()`), then bind one fixed
function per execution with `getFixedT(resolvedLocale, '<plugin-id>')`.
Never share a `t` bound to one interaction with another execution, and
never call `loadNamespaces()` per command; namespaces load once at plugin
enable time.

## German style

German translations use the informal `du` address, matching Discord
community tone. Keep it consistent: `du`, `deine`, `dir`, never `Sie` /
`Ihnen` unless quoting an external policy text.

## Locale roadmap

Pilot (frozen): `en-US`, `es-ES`, `de`. Wave 2 adds Italian, Polish, and
Greek in that order: `it`, then `pl`, then `el`. Do not add other locale
files before wave 2; unsupported codes normalize back to `en-US`.

## CI gate

`pnpm lint:locales` checks every bundle:

- key parity against `en-US` (missing key fails),
- no empty or whitespace-only values (fails),
- no uninterpolated `{var}` single-brace placeholders (fails),
- `{{variable}}` sets match `en-US`: dropped variables fail, added
  variables warn,
- every literal `t('...')` key used in `src/**/*.ts` exists in the
  `en-US` dictionaries (fails).

Translator PRs never touch integrity hashes: `scripts/generate-manifest.mjs`
excludes `**/locales/**` from `plugin-manifest.json`, so do not run
`pnpm manifest` for a locales-only change.

## Development workflow

- Dev hot-reload watches locale JSON files and calls
  `i18n.reloadResources(lng, ns)` on change. No restart needed.
- In production use the admin socket handler `admin.locales.reload`
  (optional `lng` / `ns` arguments) to reload from disk.
- The `i18next-parser` config at the repo root supports editor-side key
  extraction into `tmp/i18next-extract/`; the CI gate above remains
  authoritative.

## Third-party plugins

Publish translations with your plugin at
`data/plugins/<id>/locales/<BCP47>/common.json` using your plugin id as the
namespace. Request the `api:i18n` capability in your manifest and translate
via the host RPC call; workers have no filesystem access to locale files.
Missing locales fall back to your `en-US` strings automatically.
