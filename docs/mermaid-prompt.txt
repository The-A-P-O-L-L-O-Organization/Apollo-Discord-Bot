Generate a comprehensive Mermaid.js diagram (using graph TB / flowchart TB syntax) that visualizes the entire Apollo Discord Bot architecture. The diagram should be extremely detailed, fitting on one large page. Use subgraphs for logical grouping.

## Architecture Overview

The bot has two run modes: GATEWAY (connects to Discord via WebSocket) and WORKER (pulls jobs from BullMQ queue). Both share PostgreSQL and Redis.

## Instructions

Create a Mermaid flowchart that includes ALL of the following elements with accurate relationships:

### 1. Entry Points
- `src/index.js` — main entry, reads RUN_MODE env var, branches to gateway or worker
- `src/worker.js` — worker entry point (BullMQ consumer, no discord.js)

### 2. Core Framework
- `src/core/Plugin.js` — base class with `onLoad(eventBus)` and `onUnload(eventBus)` lifecycle hooks
- `src/core/PluginManager.js` — discovers plugins in `src/plugins/*/index.js`, loads/unloads them, handles remote install/uninstall
- `src/core/EventBus.js` — three-layer inter-plugin communication:
  - Event layer: `emit(event, data)` / `on(event, handler)`
  - API registry: `provide(name, fn)` / `call(name, ...args)` / `unprovide(name)`
  - Reactive state: `provideState(key, initial)` / `setState(key, value)` / `getState(key)` / `watchState(key, callback)`
  - Cross-pod bridging: `enableCrossPod(redisPub, redisSub, podId)` adds Redis pub/sub
- `src/core/PluginRegistry.js` — reads `data/plugin-registry.json` for remote plugins
- `src/core/pluginDownloader.js` — downloads plugin ZIP archives

### 3. Plugin Groups (src/plugins/)
Each plugin registers commands and event listeners via EventBus.

**core plugin** — `/ping`, `/help`, `/userinfo`, `/serverinfo`, `/stats`, `/reload`

**moderation plugin** — `/kick`, `/ban`, `/unban`, `/mute`, `/unmute`, `/purge`, `/warn`, `/warnings`, `/clearwarnings`, `/warnconfig`, `/blacklist`, `/case`, `/tempban`, `/automod`
- Also includes `case.js` with `createModCase()` function (used by kick/ban/mute/warn/tempban)
- Includes `guildMemberAdd.js` event handler (blacklist check, auto-role, role persistence)
- Includes `guildMemberRemove.js`, `guildMemberUpdate.js` event handlers

**automod plugin** — auto-moderation event handling
- `messageCreate.js` event handler: runs spam check, word filter, invite filter, link filter, caps filter, mention spam, account age check
- `messageDelete.js`, `messageUpdate.js` event handlers for logging

**tickets plugin** — `/ticket`, `/closeticket`, `/ticketsetup`
- Ticket creation, closing, transcript saving, DM notifications
- Panel button interaction handler

**utility plugin** — `/remind`, `/reminders`, `/cancelreminder`, `/poll`, `/reactionrole`, `/embed`, `/setlogchannel`, `/logging`
- `messageReactionAdd.js`, `messageReactionRemove.js` for reaction roles
- `voiceStateUpdate.js` for voice logging
- `interactionCreate.js` for button/select menu handlers

### 4. Queue Layer (BullMQ + Redis)
- `src/queue/queue.js` — BullMQ Queue factory with no-op fallback (when Redis unavailable)
- `src/queue/jobHandler.js` — registry: `registerHandler(jobName, fn)` / `handleJob(job)`
- `src/queue/gatewayRouter.js` — `queueOrRun(queue, job, res)` helper: enqueues expensive commands to workers
- `src/queue/metrics.js` — `getQueueMetrics()` returns waiting/active/completed/failed/delayed counts for auto-scaling
- `src/queue/jobs/processCommand.js` — processes command jobs: calls command execute, responds via REST API (interaction.followUp/editReply), handles errors

### 5. Gateway Layer
- `src/gateway/leader.js` — leader election:
  - `tryAcquireLock()`: Redis `SET apollo:lock:gateway <podId> NX PX 30000`
  - `releaseLock()`: Lua script to delete only if owner matches
  - `startHeartbeat()`: refreshes lock every 15s, handles crash recovery

### 6. Database Layer (src/db/)
- `src/db/knex.js` — Knex connection factory (PostgreSQL or SQLite fallback)
- `src/db/adapter.js` — async adapter: `getGuildData`, `setGuildData`, `updateGuildData`, `getAllGuildData`, `getUserData`, `setUserData`, `getAllUserData`, `getData`, `setData`
- `src/db/migrations/20260509_001_initial.cjs` — creates `guild_store` and `guild_user_store` tables

### 7. Utility Layer (src/utils/)
- `src/utils/db.js` — async bridge: conditionally delegates to PG adapter or wraps SQLite in Promises. Exports: `getGuildData`, `setGuildData`, `updateGuildData`, `getAllGuildData`, `getUserData`, `setUserData`, `getAllUserData`, `appendToGuildArray`, `removeFromGuildArray`, `appendToUserArray`, `removeFromUserArray`, `getData`, `setData`, `generateId`, `ensureSubDir`, `writeToSubDir`, `close`
- `src/utils/lock.js` — distributed locks: `acquireLock(redis, key, owner, ttl)`, `releaseLock(redis, key, owner)`, `withLock(redis, key, owner, fn, ttl)`, `getLockRedis()`, `closeLockRedis()`. Prefix: `apollo:lock:`
- `src/utils/modLog.js` — `sendModLog(guild, options)`, `fetchMember(guild, userId)`
- `src/utils/automod.js` — `checkSpam(message, threshold, interval)` (in-memory), `trackMessage(message)`, `checkSpamRedis(redis, message, threshold, interval)` (Redis sorted sets with TTL)
- `src/utils/raidDetection.js` — `checkRaidPattern(guildId, member)` (in-memory), `trackJoin(guildId, userId)`, `checkRaid(redis, guildId, threshold, windowMs)` (Redis)
- `src/utils/logger.js` — `logEvent(guild, eventType, embed)`, `createMemberJoinEmbed(member)`, etc.
- `src/utils/analyticsCollector.js` — `trackMemberChange(guildId, joined, memberCount)` (in-memory batching)
- `src/utils/reminderScheduler.js` — locked scheduler via `withLock(redis, 'scheduler:reminders', podId, fn, 25000)`
- `src/utils/pollScheduler.js` — locked scheduler
- `src/utils/tempbanScheduler.js` — locked scheduler + `removeTempban(guildId, userId)`, `getTempban(guildId, userId)`
- `src/utils/tempRolesScheduler.js` — locked scheduler

### 8. Configuration
- `src/config/config.js` — reads env vars: DISCORD_TOKEN, CLIENT_ID, GUILD_ID, OWNER_IDS, NODE_ENV, RUN_MODE, POD_ID, DB_TYPE, DATABASE_URL, REDIS_URL, QUEUE_PREFIX, GATEWAY_PORT

### 9. Data Flow (Critical Paths)
- **Command execution**: Discord → Gateway WebSocket → command handler → (optionally) queueOrRun → BullMQ → Worker → processCommand → REST API reply
- **Inter-plugin communication**: Plugin A emits event / calls API / sets state → EventBus → Plugin B receives
- **Cross-pod events**: Plugin emits → EventBus → Redis pub/sub → other pods receive
- **Scheduler coordination**: Worker pod calls `withLock()` → acquires Redis lock → executes scheduler → releases lock
- **Database writes**: Plugin calls `updateGuildData()` → bridge delegates to PG adapter or SQLite → returns updated data

### 10. External Infrastructure
- Discord API (WebSocket gateway + REST)
- PostgreSQL (shared multi-writer persistence, connection pool via Knex)
- Redis (BullMQ queues, distributed locks, spam/raid tracking, cross-pod EventBus pub/sub, leader election)

### 11. Test Suite
- 982 tests across 72 files in tests/
- `tests/mocks/discord.js` — MockCollection, createMockInteraction, createMockUser, createMockMember, createMockGuild, createMockChannel, createMockClient
- Vitest with vi.mock for db.js, modLog.js, config.js

## Diagram Requirements

1. Use `graph TB` (top-to-bottom)
2. Group related nodes in `<subgraph>` blocks with descriptive titles
3. Use different node shapes: `[box]` for components, `{diamond}` for decisions, `(pill)` for entry/exit points, `{{hex}}` for external services
4. Use solid arrows for direct calls (`-->`), dotted arrows for async/event-driven (`-.->`), thick arrows for data flow (`==>`)
5. Add labels on arrows describing the relationship (e.g., `|enqueues|`, `|via EventBus|`, `|acquires lock|`)
6. Add clickable styles with `click nodeId "path" "tooltip"` for source file references
7. Use different colors for different layers (green for plugins, blue for core, orange for queue, purple for DB, red for infra)
8. Include ALL source files mentioned above as nodes with their paths as tooltips

The final diagram should be comprehensive enough that someone reading it can understand the entire system architecture, all component relationships, and data flow paths without reading any other documentation.
